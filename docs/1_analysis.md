# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ

## 1.2 Аналіз існуючих аналогів

Для аналізу обрано три програмні системи: Goodreads і The StoryGraph — сервіси обліку читання, що є прямими аналогами; Habitica — сервіс гейміфікації звичок, що є опосередкованим аналогом за механізмами гейміфікації. Кожну систему розглянуто як інженерну систему за чотирма аспектами: архітектурний патерн, протоколи обміну даними, стек даних і механізми консистентності, архітектурні обмеження (technical bottlenecks). Архітектуру закритих систем (Goodreads, The StoryGraph) відновлено за інженерними публікаціями, доповідями розробників і вакансіями; архітектуру Habitica — за вихідним кодом репозиторію `HabitRPG/habitica`.

### 1.2.1 Goodreads

**Архітектурний патерн.** Система створена у 2007 році як монолітний застосунок Ruby on Rails. Після поглинання компанією Amazon у 2013 році розпочато декомпозицію моноліту на мікросервіси в інфраструктурі AWS; частину сервісів реалізовано мовою Java [1, 2]. Нові сервіси масштабуються незалежно, однак співіснування успадкованого (legacy) моноліту та мікросервісів формує гібридну архітектуру з розподіленими даними та подвійною моделлю супроводу.

**Протоколи обміну даними.** Публічний REST API (формати XML і JSON) виведено з експлуатації: видачу нових ключів припинено 08.12.2020, неактивні ключі деактивовано [3]. Сторінки видань формуються засобами Next.js із серверним рендерингом, дані сторінки вбудовуються в HTML. Окремі клієнтські запити надсилаються до GraphQL-інтерфейсу AWS AppSync; цей інтерфейс офіційно не задокументовано, відомості про нього отримано методом зворотної розробки (reverse engineering) [4].

**Стек даних і консистентність.** Історично використовувалися MySQL із шардингом і кешування Memcached [5]. У мікросервісах основним сховищем є Amazon DynamoDB (NoSQL, модель key-value). Для аналітичних запитів дані експортуються з DynamoDB до Amazon S3, перетворюються у формат Parquet засобами AWS Glue і запитуються через Amazon Athena [2]. Між мікросервісами діє модель eventual consistency; DynamoDB за замовчуванням виконує eventually consistent читання.

**Архітектурні обмеження.**

- Відсутність публічного API унеможливлює сторонні інтеграції та програмний експорт даних.
- Залежність від керованих сервісів AWS (DynamoDB, AppSync, Glue, Athena) спричиняє vendor lock-in.
- DynamoDB не оптимізована для ad hoc запитів, тому аналітика потребує окремого ETL-конвеєра; використаний у ньому сервіс AWS Data Pipeline переведено в режим підтримки [2].
- Поєднання успадкованого моноліту Ruby on Rails і мікросервісів формує технічний борг.
- Каталог поповнюється пошуком або скануванням штрихкоду ISBN для кожного примірника окремо; пакетне розпізнавання полиці не передбачено.

### 1.2.2 The StoryGraph

**Архітектурний патерн.** Монолітний застосунок Ruby on Rails, який супроводжує один розробник; клієнтами є вебверсія, iOS- і Android-застосунки [6]. Фонові задачі виконуються засобами Sidekiq на основі Redis. Для ML-функцій (близько десяти моделей: класифікація настрою видання, рекомендації, генерування персоналізованого опису мовною моделлю, перевірка обкладинок методами комп’ютерного зору) виділено кластер GPU-обробників (workers), які отримують задачі з черги Redis командою `BRPOP` [7]. Масштабування здійснюється горизонтальним додаванням вебсерверів за балансувальником HAProxy і вертикальним нарощуванням ресурсів серверів.

**Протоколи обміну даними.** Клієнти взаємодіють із Rails-застосунком за протоколом HTTP/HTTPS через балансувальник HAProxy. Взаємодія з ML-обробниками асинхронна, через черги Redis, без відкриття мережевих портів на обробниках [7]. Публічний API не надається.

**Стек даних і консистентність.** До січня 2024 року використовувалася PostgreSQL, після чого систему переведено на YugabyteDB — розподілену СУБД, сумісну з PostgreSQL; кластер із 10 серверів розширено до 60 у січні 2025 року. Додатково застосовуються Elasticsearch для пошуку, Memcached для кешування, Redis для черг і PgBouncer для пулу з’єднань. Консистентність похідних даних підтримується денормалізованими таблицями, що оновлюються зворотними викликами (callbacks) Rails; для розвантаження читання застосовувалися репліки, проблеми синхронізації яких не усунено [7].

**Архітектурні обмеження.** Задокументовано такі інциденти [7]:

- червень 2020 року — двотижнева недоступність сервісу після зростання кількості користувачів до ~20 000;
- січень 2024 року — перевантаження СУБД масовим імпортом із Goodreads (~100 000 імпортів, за оцінкою ~1 млрд операцій вставки), функцію імпорту тимчасово вимкнено;
- листопад 2024 року — зростання кількості щоденних унікальних відвідувачів зі 150 000 до 1 000 000 і насичення мережевого каналу HAProxy за низького завантаження CPU;
- січень 2025 року — нерівномірний розподіл сесій через cookie прив’язки до сервера (700–800 сесій на двох серверах проти ~20 на кожному з решти).

Після міграції на YugabyteDB час виконання окремих запитів до оптимізації зріс зі 100 мс до 400 с. Масовий імпорт не ізольовано від основного навантаження. Вартість інфраструктури Heroku перевищувала 100 000 USD на рік, що зумовило перехід на виділені сервери Hetzner [7, 8]. Супровід системи одним розробником означає концентрацію знань в одній особі (bus factor = 1).

### 1.2.3 Habitica

**Архітектурний патерн.** Монолітний сервер на Node.js 20 і Express 4 із вебклієнтом на Vue.js (SPA); каталог `website/common` містить спільний код сервера й клієнта. Мобільні клієнти реалізовано окремими нативними застосунками. Фонові задачі виконуються засобами BullMQ на основі Redis [9]. Сервер не зберігає стан між запитами (stateless) і масштабується горизонтально; межею масштабування є СУБД MongoDB.

**Протоколи обміну даними.** REST API версій v3 і v4 (JSON поверх HTTPS) з автентифікацією за ідентифікатором користувача та API-ключем; вихідні webhooks (HTTP POST) для подій задач. Автентифікацію реалізовано засобами Passport, для сторонніх провайдерів — JWT і JWKS; push-сповіщення надсилаються через Firebase Admin [9, 10].

**Стек даних і консистентність.** MongoDB з ODM Mongoose в обов’язковому режимі replica set, оскільки застосовуються change streams і багатодокументні транзакції [10]. Redis зберігає лічильники обмеження частоти запитів (бібліотека rate-limiter-flexible) і черги BullMQ. Стан гравця (досвід, рівень, предмети) зберігається денормалізовано в документі користувача.

**Архітектурні обмеження.**

- Денний цикл гейміфікації (cron: скидання щоденних задач, нарахування шкоди за пропущені задачі) запускається під час першого входу користувача в новий день, тобто синхронно в межах запиту клієнта [11]. Наслідками є додаткова затримка першого запиту, залежність стану від активності клієнта та ускладнення інтеграцій, які зчитують стан до перерахунку [12].
- Агрегування стану гравця в одному документі MongoDB ускладнює конкурентні оновлення та аудит історії змін.
- Документна модель без журналу подій не дає змоги перерахувати стан після зміни правил нарахування.

### 1.2.4 Порівняльна інженерна матриця

Порівняння виконано за шістьма технічними критеріями. Критерій швидкодії (Latency, RPS) не застосовано: для закритих систем порівнянні вимірювання відсутні, а для проєктованої системи їх буде отримано на етапі навантажувального тестування засобами k6.

| Критерій | Goodreads | The StoryGraph | Habitica | BookOff (проєктована система) |
|---|---|---|---|---|
| Тип архітектури | Гібрид: успадкований моноліт Ruby on Rails і мікросервіси (Java) в AWS | Моноліт Ruby on Rails і кластер GPU-обробників для ML | Моноліт Node.js / Express, вебклієнт Vue.js | Подієво-орієнтований модульний моноліт; сканер — окремий обробник |
| Протоколи обміну | REST API виведено з експлуатації (2020); серверний рендеринг Next.js; GraphQL (AWS AppSync, недокументований) | HTTP/HTTPS без публічного API; черги Redis до ML-обробників | REST API v3/v4 (JSON), вихідні webhooks | REST API (FastAPI, OpenAPI); події Apache Kafka; черга задач Celery |

### 1.2.5 Аналітичний висновок

Порівняльний аналіз виявив дві групи архітектурних рішень, що обмежують аналоги. Перша група — виконання ресурсомістких і масових операцій в основному контурі обробки запитів. У The StoryGraph масовий імпорт даних не ізольовано від основного навантаження, що у січні 2024 року призвело до перевантаження СУБД і вимушеного вимкнення функції імпорту. У Habitica денний цикл гейміфікації виконується синхронно під час першого запиту клієнта, що збільшує затримку відповіді та робить стан залежним від активності клієнта. Друга група — зберігання похідного стану без журналу подій: денормалізація зворотними викликами Rails у The StoryGraph і агрегований документ користувача в Habitica не забезпечують однократного врахування дій і не дають змоги перерахувати стан після зміни правил нарахування. Goodreads реалізує протилежний підхід: декомпозиція на мікросервіси з керованими сервісами AWS забезпечила незалежне масштабування ціною vendor lock-in, eventual consistency між сервісами та окремого ETL-конвеєра для аналітики.

Обраний технологічний стек усуває виявлені обмеження. Розпізнавання книжкових полиць винесено в окремий контейнер-обробник Celery, тому навантаження PaddleOCR ізольовано від API FastAPI і масштабується незалежно. Дія користувача та подія про неї фіксуються в одній транзакції PostgreSQL (Transactional Outbox) і передаються в Apache Kafka; ідемпотентні споживачі нараховують показники гейміфікації асинхронно, без збільшення затримки запиту, а CQRS-проєкції перераховуються повторним відтворенням подій. Залежність від зовнішнього бібліографічного API обмежено адаптером із Circuit Breaker, Retry, кешем і резервним джерелом Open Library; виведення з експлуатації API Goodreads підтверджує доцільність такого рішення. Розгортання засобами Docker Compose та OpenTofu не прив’язане до керованих сервісів конкретного хмарного провайдера.

Архітектурний компроміс полягає в такому. Запозичено асинхронну обробку ML-задач у виділених обробниках через чергу (The StoryGraph), обмеження частоти запитів на основі Redis (Habitica) та ізоляцію даних у межах зони відповідальності (Goodreads) — у формі окремої схеми PostgreSQL на модуль без розподілу на мікросервіси. Мікросервісну декомпозицію відхилено: для системи, яку супроводжує один розробник, вона збільшує операційні витрати без пропорційного виграшу. Ціною обраного рішення є експлуатаційна складність Apache Kafka і ретранслятора outbox, а також eventual consistency проєкцій гейміфікації, яку компенсує ідемпотентна обробка подій. Визначені рішення формалізовано в Розділі 2: декомпозиція системи на модулі за bounded contexts, моделі C4 і UML та специфікація схем подій.
