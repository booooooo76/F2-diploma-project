## 1. System Context (Контекст системи)

### 1.1 Призначення

Система призначена для ведення особистої бібліотеки друкованих видань, обліку читацької активності та нарахування показників гейміфікації. Ключова функція — ідентифікація видань за зображенням книжкової полиці.

### 1.2 Межі системи (Scope)

До меж системи належать:

- вебклієнт (SPA) і Android-клієнт, зібраний із тієї самої кодової бази засобами Capacitor;
- серверний застосунок (API) у формі модульного моноліту з модулями: ідентифікація та доступ, каталог і бібліотека, сканер полиці, читання, нотатки, гейміфікація;
- асинхронні процеси: обробник розпізнавання зображень, ретранслятор outbox, споживачі подій гейміфікації;
- сховища даних: PostgreSQL, Redis, Apache Kafka, S3-сумісне сховище зображень;
- контур спостережуваності: OpenTelemetry Collector, Prometheus, Grafana.

Поза межами системи: iOS-клієнт, соціальні функції (клуби, стрічка, обговорення), взаємодія в реальному часі, відновлення пароля через електронну пошту, автентифікація через зовнішнього провайдера ідентичності, навчання власних моделей розпізнавання.

### 1.3 Зовнішні сутності та інтерфейси

| Сутність | Тип | Інтерфейс |
|---|---|---|
| Читач | Користувач | Вебклієнт або Android-клієнт; REST API через HTTPS |
| Адміністратор | Користувач | Адміністративний розділ вебклієнта; REST API через HTTPS |
| Google Books API | Зовнішня система | REST / HTTPS, JSON |
| Open Library API | Зовнішня система (резервне джерело) | REST / HTTPS, JSON |
| Камера пристрою | Апаратний інтерфейс клієнта | Capacitor Camera API, Web MediaDevices API |

### 1.4 Обмеження

- **C-01.** Розгортання на одній хмарній віртуальній машині: 4 vCPU, 8 ГБ RAM, 80 ГБ SSD.
- **C-02.** Розпізнавання виконується на CPU без GPU; власні моделі не навчаються.
- **C-03.** Система супроводжується одним розробником.
- **C-04.** Мова інтерфейсу — українська.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

Цільове середовище вимірювань — обмеження [C-01](#14-обмеження). Навантажувальні профілі описано в розділі 4.

### 3.1 Продуктивність і масштабованість

| ID | Вимога |
|---|---|
| <a id="srs-nfr-perf-01"></a>SRS-NFR-PERF-01 | Запити читання `GET /api/v1/library`, `GET /api/v1/stats`, `GET /api/v1/gamification/profile` повинні виконуватися з p95 ≤ 300 мс і p99 ≤ 800 мс за сталої інтенсивності 100 RPS протягом 10 хв; частка відповідей 5xx — менше 0,5 %. |
| <a id="srs-nfr-perf-02"></a>SRS-NFR-PERF-02 | Запити запису `POST /api/v1/reading-sessions`, `POST /api/v1/notes` повинні виконуватися з p95 ≤ 400 мс за інтенсивності 30 RPS. |
| <a id="srs-nfr-perf-03"></a>SRS-NFR-PERF-03 | Прийом зображення розміром до 10 МБ повинен завершуватися відповіддю 202 Accepted з p95 ≤ 1 с. |
| <a id="srs-nfr-perf-04"></a>SRS-NFR-PERF-04 | Повна обробка зображення полиці (до 30 корінців, до 12 Мп) одним обробником з лімітом 2 vCPU повинна завершуватися з p95 ≤ 30 с. |
| <a id="srs-nfr-perf-05"></a>SRS-NFR-PERF-05 | Затримка від коміту транзакції з подією до оновлення проєкції гейміфікації повинна становити p95 ≤ 5 с. |
| <a id="srs-nfr-perf-06"></a>SRS-NFR-PERF-06 | Пошук у каталозі за ключем, наявним у кеші, повинен виконуватися з p95 ≤ 100 мс; частка влучань у кеш на повторних запитах — не менше 60 %. |
| <a id="srs-nfr-scal-01"></a>SRS-NFR-SCAL-01 | Кількість обробників розпізнавання та споживачів подій повинна змінюватися без змін коду (`docker compose up --scale`); два обробники повинні обробляти чергу з 8 зображень щонайменше в 1,8 раза швидше за один. |
| <a id="srs-nfr-scal-02"></a>SRS-NFR-SCAL-02 | Кожен контейнер повинен мати ліміт пам’яті: API — 512 МБ, обробник розпізнавання — 2 ГБ, Apache Kafka — 1 ГБ, PostgreSQL — 1 ГБ. |

### 3.2 Якість розпізнавання

| ID | Вимога |
|---|---|
| <a id="srs-nfr-qual-01"></a>SRS-NFR-QUAL-01 | На власному тестовому наборі з 40–60 зображень полиць система повинна забезпечувати precision ≥ 0,85 і recall ≥ 0,60. Кандидат вважається правильним, якщо його нормалізована назва збігається з еталонною за метрикою token set ratio ≥ 90. |

### 3.3 Безпека

| ID | Вимога |
|---|---|
| <a id="srs-nfr-sec-01"></a>SRS-NFR-SEC-01 | Пароль повинен мати довжину від 12 до 128 символів і не міститися в локальному списку зі 100 000 найпоширеніших скомпрометованих паролів. |
| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Паролі повинні зберігатися у вигляді хешу Argon2id з параметрами m = 19 МіБ, t = 2, p = 1. |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Access-токен JWT повинен підписуватися алгоритмом ES256 і мати строк дії 15 хв. Refresh-токен повинен бути одноразовим зі строком дії 30 днів; повторне пред’явлення використаного refresh-токена повинно анулювати всі токени цієї сесії. |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Після 5 невдалих спроб входу за 15 хв для одного облікового запису система повинна відхиляти спроби входу для нього протягом 15 хв; для кінцевих точок `/api/v1/auth/*` діє ліміт 20 запитів за хвилину з однієї IP-адреси. |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Обмеження частоти запитів (Token Bucket) повинно становити 60 запитів за хвилину на користувача для API і 10 зображень за годину для сканера; перевищення повинно повертати 429 Too Many Requests із заголовком Retry-After. |
| <a id="srs-nfr-sec-06"></a>SRS-NFR-SEC-06 | Доступ до ресурсів повинен перевірятися за роллю (reader, admin) і за належністю ресурсу користувачу; запит до чужого ресурсу повинен повертати 404 Not Found. |
| <a id="srs-nfr-sec-07"></a>SRS-NFR-SEC-07 | Зовнішній трафік повинен передаватися лише через TLS 1.2 або 1.3 із заголовком HSTS (max-age ≥ 31 536 000 с); CORS повинен дозволяти лише домен вебклієнта. |
| <a id="srs-nfr-sec-08"></a>SRS-NFR-SEC-08 | Зображення повинні прийматися лише у форматах JPEG, PNG або WebP за сигнатурою файлу та розміром до 10 МБ; EXIF-метадані повинні видалятися до збереження; зображення повинні видалятися зі сховища через 24 год. |
| <a id="srs-nfr-sec-09"></a>SRS-NFR-SEC-09 | Секрети (ключі підпису JWT, паролі СУБД, ключі сховища) не повинні зберігатися в репозиторії; вони передаються контейнерам через Docker secrets. |
| <a id="srs-nfr-sec-10"></a>SRS-NFR-SEC-10 | Події безпеки (вхід, невдалий вхід, вихід, повторне використання refresh-токена, видалення облікового запису) повинні журналюватися без паролів і токенів; строк зберігання журналу — 30 днів. |
| <a id="srs-nfr-sec-11"></a>SRS-NFR-SEC-11 | Система повинна відповідати OWASP ASVS L1. У CI-конвеєрі: SonarQube Quality Gate — пройдено; Trivy — 0 вразливостей рівнів Critical і High; Gitleaks — 0 знахідок; OWASP ZAP Baseline — 0 попереджень рівня High. |

## 5. Glossary (Глосарій)

| Термін | Визначення |
|---|---|
| Корінець | Вузька бічна частина обкладинки книги, видима на полиці; містить назву та автора, як правило повернуті на ±90°. |
| Подія активності | Незмінний запис про дію користувача (додавання видання, завершення сесії читання, створення нотатки), з якого обчислюються показники гейміфікації. |
| Transactional Outbox | Патерн, за якого подія записується в таблицю outbox у тій самій транзакції, що й доменні дані, а окремий ретранслятор передає її в брокер повідомлень. |
| Idempotent Consumer | Споживач подій, що зберігає ідентифікатори оброблених подій і не змінює стан за повторної доставки тієї самої події. |
| CQRS-проєкція | Таблиця, оптимізована для читання, що будується з потоку подій окремо від моделі запису і може бути перебудована повторним відтворенням подій. |
| Eventual consistency | Модель узгодженості, за якої похідні дані досягають узгодженого стану з певною затримкою після зміни джерела. |
| p95 Latency | Значення часу відповіді, яке не перевищують 95 % запитів у вибірці вимірювань. |
| JWT | JSON Web Token (RFC 7519) — підписаний токен з набором тверджень про користувача, що використовується для автентифікації запитів без звернення до сховища сесій. |
| Circuit Breaker | Патерн, що припиняє виклики зовнішньої системи після перевищення порога помилок і відновлює їх після контрольної перевірки. |
| Precision / Recall | Частка правильних кандидатів серед знайдених / частка знайдених видань серед присутніх на зображенні. |
